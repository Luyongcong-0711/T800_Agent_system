# 系统架构与技术栈

## 总体结构

统一入口：

```text
Agent Server / Agent Runtime
```

整体结构：

```text
用户 / Web UI / CLI / 桌面端
  -> Agent Server
    -> Agent Runtime
      -> LangGraph Workflow
        -> call_model
        -> validate_tool_call
        -> policy / hook / approval
        -> execute_tool
        -> handle_tool_result
        -> final_answer
      -> Tool Registry
      -> Tool Adapter
      -> MCP Client
      -> Skill Registry
      -> Skill Runner
      -> SubAgent Manager
      -> Memory Manager
      -> Event Emitter
      -> Log Writer
      -> Observability Manager
      -> Job Scheduler
      -> Secret Store
      -> RAG / GraphRAG Pipeline
    -> MinIO
    -> Milvus
    -> Neo4j
```

## Agent Server 职责

- 接收用户请求。
- 在 P0 无登录模式下提供默认身份 `default_user / owner` 和默认 `workspace_id=default`。
- 对所有 workspace 级请求执行 scope guard，不能因为 P0 单用户就绕过 `user_id / workspace_id / role` 校验。
- 管理会话、Agent Run、后台 Job 和任务状态。
- 代理模型调用。
- 编排 LangGraph 工作流。
- 管理工具注册表。
- 连接 MCP Server。
- 调度 RAG / GraphRAG。
- 发送 SSE 事件。
- 发起审批请求。
- 写入日志和运行产物。
- 写入系统运行日志、组件日志、错误日志和诊断包。
- 调度后台 Job，包括文档入库、embedding 重建、图谱构建、日志归档、诊断包和 MCP capability refresh。
- 读取配置中心中的模型、数据库、MCP、工具权限配置。
- 提供密钥创建、禁用、轮换和引用检查 API；接口只返回 `secret_ref` 和脱敏摘要。

## Agent Runtime 职责

- 在 AgentState、Tool 参数、日志和审计事件中传递 `user_id`、`role`、`workspace_id`。
- 构建模型调用上下文。
- 根据工具 metadata 裁剪当前可用工具。
- 对 tool call 做 schema、语义、安全校验。
- 加载 Skill 的提示词、流程、知识包和脚本入口。
- 通过 Skill Runner 执行 Skill 携带的脚本，并套用沙盒、审批、日志和 ToolResult。
- 统一执行内置 Tool、数据库 Tool、MCP Tool 和 SubAgent Tool。
- 执行 Hook、审批、沙盒、重试、熔断、降级。
- 输出统一 ToolResult。
- 发出前端可渲染的事件。
- 写入脱敏日志和操作日志。
- 为每次模型调用、工具调用、MCP 调用、数据库调用和 SSE 连接写 trace/span 运行日志。
- 管理短期上下文、长期记忆、上下文压缩。
- 通过内部 `SecretResolver` 为模型、数据库和 MCP Connector 解析密钥；明文不进入模型上下文、ToolResult、SSE 事件或日志。

数据层边界：

```text
不使用 pgsql / PostgreSQL / MySQL / 独立 Catalog DB。
MinIO 的 manifest / index / JSONL / snapshot 对象承担 session、run、job、document、chunk、memory 的权威状态和轻量索引。

Milvus 只承担向量检索。
Neo4j 只承担实体关系和 GraphRAG 多跳扩展。
Redis 只承担可重建缓存，不承担锁、队列和主状态。
```

## P0 部署边界

P0 默认使用 docker compose 启动本地依赖：

```text
MinIO
Milvus
Neo4j
Redis
```

默认本地服务用于开发、测试和单机部署。数据库配置页面必须允许把 MinIO、Milvus、Neo4j、Redis 切换为远程服务；前端保存 endpoint / uri 和 secret_ref，后端 Connector 内部解密并连接。Redis 仍只作为可重建缓存，不因为远程部署而变成队列、锁或主状态。

## 身份与工作区边界

P0 按单用户系统实现，但数据结构保留多用户和多 workspace 扩展字段。

```text
user_id = default_user
role = owner
workspace_id = default
workspace_role = owner
login_enabled = false
workspace_switch_enabled = false
```

`workspace` 是项目空间，不是对话窗口。一个 workspace 内可以有多个 thread、知识库、文档、run、配置、日志和项目记忆。P0 前端默认进入 `workspace_id=default`，不做复杂 workspace 切换，但所有 API、MinIO object key、Tool 参数、Milvus metadata、Neo4j scope 和审计日志都必须保留 `workspace_id`。

长期记忆 scope：

| 类型 | Scope |
| --- | --- |
| `user_profile` | global |
| `user_preference` | global 或 workspace |
| `project_fact` | workspace |
| `project_rule` | workspace |

## 关键原则

- 模型只能通过 Tool 调用数据库、文件、网络和 MCP，不直接持有连接凭证，也不能调用 SecretResolver。
- 配置对象只保存 `api_key_ref`、`access_key_ref`、`secret_key_ref`、`token_ref`、`credential_ref`、`headers_ref` 等引用；后端 Connector 在内部解析明文。
- 任何副作用操作必须带 `operation_id`。
- 任何高风险操作必须进入 Hook / 沙盒 / 审批链路。
- 日志由系统写入，模型只能读取脱敏摘要。
- run event / audit 不等于完整系统日志；系统运行日志必须覆盖 API、Runtime、MCP、模型、数据库、SSE、后台任务、缓存、SecretResolver、IndexRebuilder 等组件。
- Run 和 Job 必须分开；Job 不复用 run event 路径，不使用 Redis 队列，权威状态保存在 MinIO。
- 系统运行日志采用本地热日志 + MinIO 归档，避免 MinIO 故障时无法排查。
- 失败处理先分类，再决定重试、修复、降级、询问用户或拒绝。
