## 协议分层

底层连接：

| 术语 | 含义 |
| --- | --- |
| TCP | 可靠底层连接 |
| TLS | 加密层 |
| HTTP | 常见请求 / 响应协议 |
| HTTPS | HTTP + TLS |
| WebSocket | 双向长连接 |

HTTP 上的传输方式：

| 方式 | 典型用途 |
| --- | --- |
| 普通 HTTP 请求 | 登录、查询、提交表单、普通 API |
| SSE | 服务端持续向客户端推送，适合 LLM token 流 |
| Streamable HTTP | 远程 MCP 工具通信 |

应用协议：

| 协议 | 用途 |
| --- | --- |
| OpenAI / Anthropic API | 模型调用规则 |
| MCP | Agent 调工具协议 |
| A2A | Agent 和 Agent 协作协议 |
| JSON-RPC | JSON 调用消息格式 |
| REST | HTTP API 风格 |

核心原则：

```text
自己控制两端时，可以选择协议。
连接外部服务时，必须使用对方支持的协议。
```

## SSE 与控制接口

SSE 适合：

```text
文字 Agent 流式输出
工具调用状态单向推送
任务进度单向推送
```

事件示例：

```text
event: token
data: {"text":"你好"}

event: tool_call
data: {"name":"vector_search","args":{"query":"..."}}

event: tool_result
data: {"name":"vector_search","summary":"found 3 results"}

event: final
data: {"answer":"..."}
```

当前决策：

```text
当前设计不使用 WebSocket。
文字 Agent 流式输出、工具状态、任务进度统一使用 HTTPS + SSE。
用户打断、审批确认、审批拒绝、配置保存、文件上传等控制动作统一使用 HTTPS REST。
```

控制接口示例：

| 操作 | 方式 | 说明 |
| --- | --- | --- |
| 创建对话 | POST /threads | 创建一个新的前端可见对话窗口 |
| 查询对话列表 | GET /threads | 左侧历史会话列表 |
| 查询对话详情 | GET /threads/{thread_id} | 打开旧对话，读取 manifest 摘要 |

## 多对话窗口 REST 接口

`thread_id` 是前端左侧历史列表中的一个对话窗口。`run_id` 是某个 thread 内一次用户提交后的 Agent 执行。

### POST /threads

创建新对话，不会删除旧对话。

请求：

```json
{
  "workspace_id": "default",
  "title": null,
  "knowledge_base_id": "kb_default",
  "initial_model_config_version": "modelcfg_004"
}
```

返回：

```json
{
  "thread_id": "thread_001",
  "title": "新对话",
  "status": "active",
  "manifest_object_key": "workspaces/default/sessions/thread_001/manifest.json"
}
```

流程：

```text
1. 生成 thread_id。
2. 写 sessions/{thread_id}/manifest.json。
3. 写 sessions/{thread_id}/messages/message_index.json 空索引。
4. 写 sessions/{thread_id}/runs_index.json 空索引。
5. 更新 indexes/threads_index.json。
6. 返回 thread 摘要。
```


返回：

```json
{
  "threads": [
    {
```

### POST /threads/{thread_id}/runs

在当前对话里提交用户消息并启动 Agent run。

请求：

```json
{
  "message": {
    "content_type": "text",
    "content": "继续修改多对话窗口设计"
  },
  "knowledge_base_id": "kb_default",
  "idempotency_key": "idem_thread_001_msg_001"
}
```

返回：

```json
{
  "thread_id": "thread_001",
  "run_id": "run_004",
  "user_message_id": "msg_thread_001_000000000031",
  "events_stream_url": "/runs/run_004/events/stream"
}
```

流程：

```text
1. 校验 thread 存在、未 soft_deleted、当前用户可访问。
2. 按 idempotency_key 判断是否重复提交。
3. 追加 user message 到 sessions/{thread_id}/messages/part-*.jsonl。
4. 更新 message_index、thread manifest、threads_index。
5. 创建 runs/{run_id}/manifest.json、event_index.json、leaf_state.json。
6. 写 run_started / user_message 事件。
7. 更新 workspace runs_index 和 thread runs_index。
8. 返回 run_id，前端再连接 SSE。
```

### PATCH /threads/{thread_id}

用于重命名、置顶、归档、恢复归档。

请求：

```json
{
  "title": "Agent 系统最终设计",
  "pinned": true,
  "status": "active"
}
```

### DELETE /threads/{thread_id}

默认软删除，不物理删除消息、run、日志和产物。

流程：

```text
1. 设置 thread manifest status=soft_deleted。
2. 设置 soft_deleted=true 和 deleted_at。
3. 更新 threads_index。
4. 如果存在 running run，先要求用户取消或等待结束。
```

## 通用重连原则

- 所有外部连接必须有 timeout。
- 重试使用指数退避和 jitter。
- 所有重试受 `retry_budget`、`max_total_latency`、`max_external_calls` 限制。
- 可重试错误和不可重试错误必须分类。
- 有副作用操作必须使用 `operation_id` 和幂等键。
- `unknown_outcome` 先查状态，不能盲目重试。
- 同一服务连续失败后进入熔断，避免重试风暴。

## 前端 SSE 断线重连

前端与 Agent Server 的 SSE 用于展示 token、工具状态、审批状态和任务进度。

机制：

```text
1. 前端使用 fetch + ReadableStream 建立 SSE 读取流。
2. Server 为每个持久化事件分配递增 event_seq 和 event_id。
3. Server 先把可恢复事件写入 MinIO events/part-*.jsonl，再发送 SSE。
4. 前端记录最后处理成功的 last_event_id。
5. 断线后带 Last-Event-ID header 或 after_event_id query 重新连接。
6. Server 根据 event_index.json 定位分段，从 MinIO 补发未收到事件。
7. 如果 run 仍 active，补齐历史后继续发送实时事件。
8. 如果 run 已 finished，补齐历史后发送 stream_closed 并关闭 SSE。
```

SSE 事件必须包含：

```json
{
  "event_seq": 123,
  "event_id": "evt_run_001_000000000123",
  "run_id": "run_001",
  "thread_id": "thread_001",
  "trace_id": "trace_001",
  "type": "tool_status",
  "created_at": "2026-05-28T12:00:00+08:00"
}
```

SSE wire 格式：

```text
id: evt_run_001_000000000123
event: tool_call_update
data: {"event_seq":123,"event_id":"evt_run_001_000000000123","run_id":"run_001","type":"tool_call_update","tool_call_id":"call_001","status":"running"}
```

断线重连接口：

| 接口 | 用途 |
| --- | --- |
| `GET /runs/{run_id}/events/stream` | SSE 实时流，支持 `Last-Event-ID` |
| `GET /runs/{run_id}/events?after_event_id=...&limit=...` | REST 历史事件分页 |
| `GET /runs/{run_id}` | run 当前快照，读取 `leaf_state.json` |

Server 处理 `Last-Event-ID`：

```text
1. 解析 Last-Event-ID 得到 after_event_seq。
2. 读取 runs/{run_id}/event_index.json。
3. 找到 last_event_seq > after_event_seq 的第一个 segment。
4. 读取 segment JSONL，过滤 event_seq > after_event_seq。
5. 按 event_seq 升序补发。
6. 补发完成后，如果 run.status 是 running / waiting_approval / recovering，继续挂实时流。
7. 如果 run.status 是 completed / failed / cancelled，发送 final snapshot 后关闭。
```

## Job SSE 断线重连

Job SSE 与 Run SSE 采用同一套 `fetch + ReadableStream` 客户端形态，但事件路径和恢复对象分开。

接口：

| 接口 | 用途 |
| --- | --- |
| `GET /workspaces/{workspace_id}/jobs/{job_id}/events/stream` | Job SSE 实时流，支持 `Last-Event-ID` |
| `GET /workspaces/{workspace_id}/jobs/{job_id}/events?after_event_id=...&limit=...` | Job REST 历史事件分页 |
| `GET /workspaces/{workspace_id}/jobs/{job_id}` | Job 当前快照，读取 `leaf_state.json` |

恢复流程：

```text
1. 前端任务中心记录每个 job_id 的 last_event_id。
2. 页面刷新后先调用 GET /workspaces/{workspace_id}/jobs/{job_id} 读取 leaf_state。
3. 如果 Job status 是 running / waiting_retry / recovering / unknown_outcome，连接 Job SSE。
4. 连接时带 Last-Event-ID header 或 after_event_id query。
5. Server 读取 jobs/{job_id}/event_index.json。
6. 从 jobs/{job_id}/events/part-*.jsonl 补发 event_seq 更大的事件。
7. 补发完成后，如果 Job 仍非终态，继续挂实时流。
8. 如果 Job 已 succeeded / failed / cancelled，发送 stream_closed 并关闭。
```

前端去重规则：

- Job 事件使用 `event_id` 去重。
- Job 事件 ID 格式为 `evt_{job_id}_{event_seq_12位补零}`。
- `run_id` 和 `job_id` 的 last_event_id 分开存储，不能混用。
- 同一个任务中心页面同时订阅的 active Job 默认最多 5 个；超过后用 `GET /jobs` 摘要刷新。
- Job 事件只更新任务中心、文档详情、知识库页或配置页状态，不直接追加到 thread messages。

前端去重规则：

- 前端用 `event_id` 做幂等去重。
- 如果收到相同 `event_id`，忽略后到事件。
- 如果收到 `event_seq` 跳号，立即调用 REST 历史分页补齐缺口。
- 前端只在事件渲染成功后更新本地 `last_event_id`。
- 浏览器刷新后，先调用 `GET /runs/{run_id}` 拿 `leaf_state`，再从本地或服务端记录的 `last_event_id` 补事件。
- 用户切换到旧 thread 时，先通过 `AbortController` 停止当前页面上的 SSE 订阅；如果旧 thread 的 `current_run_status` 是 running / waiting_approval / recovering，再连接该 run 的 SSE。
- 用户切换到已完成 thread 时，只读 `GET /threads/{thread_id}/messages` 和必要的 run 快照，不保持 SSE。
- 同一个浏览器标签同一时刻默认只订阅当前打开 thread 的 active run；后台 thread 的运行状态通过 `GET /threads` 摘要刷新。

事件持久化与实时发送顺序：

- `run_started`、`user_message`、`tool_call_*`、`approval_*`、`operation_*`、`compaction_*`、`assistant_message` 必须先落 MinIO 后发送。
- 高频 token 可以先通过 SSE 发送临时 `token` 事件，但必须定期聚合为可恢复的 `assistant_delta` 持久化事件。
- 前端恢复不能依赖未持久化 token，只依赖 `assistant_delta` 和最终 `assistant_message`。
- 如果持久化失败，Server 不得假装事件已成功；必须发送 `stream_error`，并让前端读取 run 快照。

## 普通 API 重试

适用：

- 创建 thread。
- 读取 thread 列表和历史消息。
- 配置保存。
- 任务查询。
- 文件上传初始化。
- 审批确认。

规则：

- GET 查询类接口可以自动重试。
- POST 写操作必须带 `idempotency_key`。
- `POST /threads/{thread_id}/runs` 超时后不能直接重复创建 run，必须先用 `idempotency_key` 查询是否已经生成 `run_id`。
- 审批确认必须带 `approval_id` 和当前版本号。
- 客户端超时后不直接重复写操作，先查询操作状态。

## LLM API 断线处理

P0 模型 Provider 范围：

```text
OpenAI-compatible
Anthropic
```

Gemini、OpenRouter、本地模型、Ollama、LM Studio 放到 P1。

所有 Provider 原始响应必须先进入 Provider Adapter，转换为统一 `ModelStreamEvent`、`ModelResult`、`ModelUsage` 和 `ModelError`，再由 Agent Server 转成前端 SSE 事件。前端不理解供应商原始流格式。

非流式调用：

- 408、429、短暂 5xx、timeout 可重试。
- 400、401、403、模型不存在不可重试。
- 超过预算后切换备用模型或询问用户。

流式调用：

- 大多数模型流断开后无法从中间 token 原样续传。
- Runtime 记录已输出 token、trace_id 和模型调用状态。
- 如果模型调用没有副作用，可从 LangGraph checkpoint 重新调用。
- 如果已向用户展示部分 token，前端需要标记“当前回答已中断，正在恢复”。
- 恢复时可以重新生成完整答案，也可以要求模型基于已完成摘要继续，但不能假装是同一条原始流无缝继续。

context overflow：

- Runtime 调用前发现 `prompt_tokens + max_output_tokens > context_window_tokens` 时，先触发 Hermes 压缩。
- Provider 返回 context length exceeded / token limit exceeded 时，统一分类为 `context_overflow`。
- `context_overflow` 只允许自动压缩并重试一次。
- 重试后仍失败时，写 `model_call_failed` 事件，并向用户显示“上下文超长，已压缩重试仍失败”的可见错误。

## Embedding API 重试

- 入库批处理按 batch 记录 checkpoint。
- 单个 batch 失败只重试该 batch。
- 429 和短暂 5xx 可重试。
- 维度不匹配、模型不存在、API key 无效不可重试。
- 失败后保留 chunk JSON，manifest 标记 embedding failed，可人工或定时重试。

## Milvus 重连

- 使用 Connector 维护客户端和连接健康检查。
- timeout、connection reset、短暂不可用可重试。
- collection 不存在、维度不匹配、字段 schema 不匹配不可重试。
- 检索超时后可降低 top_k 或直接降级到 Neo4j 只读扩展，但需要向答案标明文本召回不足。
- 写入失败时用 `operation_id` 去重，避免重复插入。

## Neo4j 重连

- 使用 Driver / Bolt 连接池。
- TransientError、连接重置、短暂 timeout 可重试。
- Cypher 语法错误可交给模型修复，但不作为网络重连。
- 权限错误、label 不在白名单、写语句被拦截不可重试。
- 图查询失败时可退回 Milvus 文本证据回答。

## MinIO 重连

- 普通读取失败可重试。
- 大文件上传使用 multipart upload。
- 上传断开后优先查询已上传 part，再继续上传。
- 原始文件上传未完成时不进入解析。
- manifest 更新失败时要写入错误日志，并通过对象存在性检查恢复。

## MCP stdio 重连

stdio MCP 是本地子进程通信，断线可能来自进程退出、stdout 协议错误、初始化失败。

恢复流程：

```text
1. 标记 server 为 disconnected。
2. 停止当前子进程，收集 stderr 摘要。
3. 根据 restart policy 判断是否可自动重启。
4. 重新启动进程。
5. 重新发送 initialize。
6. 重新执行 tools/list、resources/list、prompts/list。
7. 更新 capability snapshot。
8. 失败超过阈值后熔断，要求用户检查配置。
```

进行中的 MCP tool call 如果断线：

- 读操作可按工具重试策略重试。
- 写操作进入 `unknown_outcome`，先查状态或要求用户确认。

## MCP Streamable HTTP 重连

- HTTP 408、429、短暂 5xx 可重试。
- 401、403、server not found 不可重试。
- 会话型远程 MCP 需要保存 session id。
- 重连后先校验 server capability 是否变化。
- capability 变化时刷新工具列表，并让 Runtime 重新裁剪可用工具。

## 旧 SSE MCP 重连

- 使用 EventSource 重连语义。
- 记录最后事件 ID。
- 如果服务端不支持断点续传，只能重新初始化 capability。
- 标记为兼容模式，并在配置页提示风险。

## 外部模型协议限制

不能单方面把普通 HTTPS 模型 API 改成其他长连接协议。

模型普通文本 API 通常是：

```text
HTTPS POST
```

流式输出通常是：

```text
HTTPS + SSE
```

只有 endpoint 明确支持特定实时协议时，才能使用该协议。
