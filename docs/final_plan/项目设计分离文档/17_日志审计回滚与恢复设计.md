## 日志原则

日志由系统写，不由模型写。

本文件主要描述 run event、job event、审计、回滚和恢复日志。完整系统运行日志、组件日志、错误快查日志、诊断包和 LogShipper 设计见 `32_系统运行日志与可观测性设计.md`。Codex/SubAgent 开发过程日志见 `33_Codex开发日志与SubAgent开发流程设计.md`。后台 Job 的调度、状态机、owner/fencing 和任务中心接口见 `34_后台任务Job调度与恢复设计.md`。

写日志的层：

```text
Agent Runtime
Tool Executor
Connector
UI / Client
RollbackManager
Observability Manager
Job Scheduler
Development Log Writer
```

## 日志位置

第一版使用 MinIO JSONL：

```text
workspaces/{workspace_id}/runs/{run_id}/manifest.json
workspaces/{workspace_id}/runs/{run_id}/events/part-000001.jsonl
workspaces/{workspace_id}/runs/{run_id}/event_index.json
workspaces/{workspace_id}/runs/{run_id}/leaf_state.json
workspaces/{workspace_id}/runs/{run_id}/tool_inventory_snapshot.json
workspaces/{workspace_id}/runs/{run_id}/tool_calls.jsonl
workspaces/{workspace_id}/runs/{run_id}/errors.jsonl
workspaces/{workspace_id}/runs/{run_id}/operations.jsonl
workspaces/{workspace_id}/jobs/{job_id}/manifest.json
workspaces/{workspace_id}/jobs/{job_id}/events/part-000001.jsonl
workspaces/{workspace_id}/jobs/{job_id}/event_index.json
workspaces/{workspace_id}/jobs/{job_id}/leaf_state.json
workspaces/{workspace_id}/jobs/{job_id}/errors.jsonl
workspaces/{workspace_id}/runs/{run_id}/skill_runs/{skill_run_id}/manifest.json
workspaces/{workspace_id}/runs/{run_id}/skill_runs/{skill_run_id}/stdout.txt
workspaces/{workspace_id}/runs/{run_id}/skill_runs/{skill_run_id}/stderr.txt
workspaces/{workspace_id}/runs/{run_id}/skill_runs/{skill_run_id}/diff.patch
system/logs/{date}/{runtime_instance_id}/system_full/part-000001.jsonl
system/logs/{date}/{runtime_instance_id}/errors/part-000001.jsonl
```

MinIO 是对象存储，JSONL 写入按逻辑追加处理。P0 直接使用分段事件对象 `events/part-*.jsonl`，由 `event_index.json` 记录每个分段的事件范围。封存后的分段不可修改；当前活跃分段可以在小尺寸内重写，达到阈值后封存。

run event 日志和系统运行日志的边界：

| 类型 | 记录内容 | 存储 |
| --- | --- | --- |
| run event | 单次 Agent run 的消息、工具、审批、SSE 补发和状态恢复 | `workspaces/{workspace_id}/runs/{run_id}` |
| job event | 后台 Job 的阶段、进度、取消、重试、unknown_outcome 和恢复 | `workspaces/{workspace_id}/jobs/{job_id}` 或 `system/jobs/{job_id}` |
| operation audit | 副作用、回滚、unknown_outcome | `operations.jsonl` |
| system runtime | API、Runtime、MCP、模型、数据库、SSE、后台任务、组件异常 | 本地热日志 + `system/logs` MinIO 归档 |
| development log | Codex/SubAgent 开发任务、报告、验证、ADR | `_development_logs`，后续可同步 MinIO |

日志字段：

```json
{
  "schema_version": 1,
  "event_seq": 12,
  "event_id": "evt_run_001_000000000012",
  "created_at": "2026-05-28T11:10:00+08:00",
  "trace_id": "trace_001",
  "thread_id": "thread_001",
  "run_id": "run_001",
  "event_type": "tool_call_started",
  "tool_call_id": "call_abc",
  "tool_name": "local_file_search",
  "args_preview": {
    "query": "retry error handling",
    "root": "workspace"
  }
}
```

日志写入顺序：

```text
1. 生成 event_seq / event_id。
2. 把事件写入当前 events/part-*.jsonl。
3. 更新 event_index.json 的 last_event_seq、last_event_id、segments。
4. 根据事件更新 leaf_state.json。
5. 如果事件影响前端列表，再更新 runs_index.json。
6. 通过 SSE 发送给前端。
```

如果第 2 步成功、第 3 到 5 步失败，不回滚事件；写入 `errors.jsonl`，由 `IndexRebuilder` 从事件分段重建索引。

不要写入：

- API key。
- 数据库密码。
- `AGENT_MASTER_KEY`。
- Secret 明文。
- Secret 密文、nonce、tag。
- 完整用户隐私数据。
- 完整文件内容。
- 完整原始 headers。
- 完整 embedding 向量。
- access token。
- refresh token。

允许写入的密钥相关摘要：

- `secret_id`。
- `secret_ref`。
- `masked`。
- `secret type`。
- `purpose`。
- `status`。

必须统一脱敏的字段名：

```text
Authorization
Cookie
Set-Cookie
X-API-Key
api_key
access_key
secret_key
password
token
access_token
refresh_token
```

## 模型访问日志

模型不能直接读完整原始日志。

模型只能通过受控工具读取：

```text
get_last_error
get_tool_call_trace
summarize_recent_failures
safe_log_search
```

返回脱敏摘要：

```json
{
  "trace_id": "trace_001",
  "summary": "最近一次 Neo4j 查询失败，原因是 connection_timeout，已重试 3 次仍失败。",
  "safe_events": [
    {
      "time": "2026-05-28T11:10:03+08:00",
      "tool": "neo4j_query",
      "status": "failed",
      "error_type": "connection_timeout",
      "retryable": true,
      "attempt": 3
    }
  ],
  "redacted": true
}
```

`tool_inventory_snapshot.json` 默认不提供给模型。模型如需排查“为什么某个工具不可用”，只能通过受控日志工具获得脱敏结论，例如：

```json
{
  "summary": "mcp_filesystem_delete_file 在本次 run 中不可用，原因是用户禁用了该 MCP tool。",
  "inventory_hash": "sha256...",
  "redacted": true
}
```

Skill Script 原始日志默认不提供给模型。模型只能看到 ToolResult 中的 stdout/stderr preview、错误类型和安全摘要。完整 stdout、stderr、diff.patch 和 operation_plan 只给日志审计页面或受控日志工具使用。

Skill Script 必须写入这些事件：

```text
skill_run_started
skill_run_finished
skill_run_failed
skill_patch_staged
skill_patch_committed
skill_sandbox_cleanup_failed
```

写入型 Skill 的 `skill_patch_staged` 事件必须包含：

- skill_run_id。
- skill_id。
- skill_version。
- entrypoint。
- diff_object_key。
- operation_plan_object_key。
- changed_files。
- diff_summary。
- approval_id。

## Retry / Rollback / Compensation

区别：

```text
retry：操作没成功，重试同一个动作。
rollback：操作已经产生副作用，需要撤销。
compensation：无法真正撤销，只能做反向补偿。
```

副作用工具声明：

```json
{
  "name": "write_file",
  "risk_level": "high",
  "side_effect": true,
  "reversible": true,
  "rollback_strategy": "file_backup",
  "requires_approval": true,
  "idempotency_required": true
}
```

恢复原则：

```text
所有写操作必须有 operation_id。
所有写操作必须记录 operation_log。
工具声明 side_effect、reversible、rollback_strategy。
低风险回滚自动执行。
高风险回滚人工确认。
unknown_outcome 先查状态。
不可逆操作只能 compensation。
模型只能看脱敏日志摘要。
```

## 恢复场景

| 场景 | 恢复策略 |
| --- | --- |
| SSE 断线 | 根据 `Last-Event-ID` 读取 `event_index.json`，从 `events/part-*.jsonl` 补发事件 |
| Job SSE 断线 | 根据 `Last-Event-ID` 读取 `jobs/{job_id}/event_index.json`，从 `jobs/{job_id}/events/part-*.jsonl` 补发事件 |
| 工具执行中断 | 根据 ToolResult 和 operation_id 判断重试或 unknown_outcome |
| 文件写入失败 | 使用备份恢复或标记部分失败 |
| Milvus 写入失败 | 按 operation_id 去重重试 |
| Neo4j 写入失败 | 基础 RAG 可用，GraphRAG 降级 |
| MCP 进程退出 | 重启、初始化、刷新 capability snapshot |
| Skill 脚本超时 | kill 沙盒进程树，记录 `skill_script_timeout`，当前 run 内连续失败达到阈值时临时禁用 entrypoint |
| Skill staged patch 提交失败 | 保留 diff.patch 和 operation_plan，标记 operation unknown_outcome 或 failed，等待用户重试或回滚 |
| Job Worker 崩溃 | Job 进入 `recovering`，重放 job events，重建 `leaf_state.json`，用 owner/fencing 接管后继续或失败 |
| Job 外部写入结果未知 | 标记 `unknown_outcome`，按 operation_id 查询 MinIO / Milvus / Neo4j / MCP snapshot 后再重试或收敛为终态 |

## MinIO 状态恢复

Runtime 启动、进程崩溃、机器重启或 run 被其他实例接管时，必须执行状态恢复。

恢复入口：

```text
GET /threads/{thread_id}
GET /runs/{run_id}
Runtime recover_thread(thread_id)
Runtime recover_run(run_id)
JobScheduler recover_job(job_id)
IndexRebuilder rebuild_run(run_id)
IndexRebuilder rebuild_job(job_id)
```

run 恢复流程：

```text
1. 读取 runs/{run_id}/manifest.json。
2. 检查 run status。
3. 检查 owner.fencing_token 和 expires_at。
4. 如果当前 Runtime 无权接管，返回 read-only 状态。
5. 读取 event_index.json。
6. event_index 缺失、revision 落后或校验失败时，扫描 events/part-*.jsonl 重建。
7. 读取 leaf_state.json。
8. leaf_state 缺失或 last_event_seq 落后时，从事件重放生成。
9. 读取 operations.jsonl，找出 pending / unknown_outcome 操作。
10. 对 pending 超时副作用操作标记 unknown_outcome。
11. 恢复 pending approval 到前端。
12. run 已终态时只提供历史查询。
13. run 非终态时交给 LangGraph checkpoint 恢复，或者生成可见错误并标记 failed。
```

thread 恢复流程：

```text
1. 读取 sessions/{thread_id}/manifest.json。
2. 读取 sessions/{thread_id}/messages/message_index.json。
3. message_index 缺失、revision 落后或校验失败时，扫描 messages/part-*.jsonl 重建。
4. 读取 sessions/{thread_id}/runs_index.json。
5. runs_index 缺失或落后时，从 manifest.run_ids 和 runs/{run_id}/manifest.json 重建。
6. 如果 current_run_id 非空，读取对应 run leaf_state。
7. 如果 current run 仍 running / waiting_approval / recovering，前端可以恢复 SSE。
8. 如果 thread status 是 archived 或 soft_deleted，只提供历史查看或恢复操作，不自动启动新 run。
9. 更新 threads_index.json 摘要。
```

事件重放规则：

- 按 `event_seq` 升序处理。
- 重复 `event_id` 只处理第一次，后续记为 duplicate。
- 缺失 `event_seq` 时标记 `event_gap_detected`，run 进入 `recovering`，禁止继续执行高风险写操作。
- `assistant_delta` 只用于恢复前端显示，不作为最终回答的唯一来源。
- `assistant_message` 是 assistant 完整消息的权威事件。
- `operation_unknown_outcome` 必须显示在日志审计页面，不能被自动吞掉。

## 索引重建

`IndexRebuilder` 是后台恢复组件，不需要额外数据库。

可重建对象：

| 索引对象 | 重建来源 |
| --- | --- |
| `threads_index.json` | `sessions/*/manifest.json` + `message_index.json` + `runs_index.json` |
| `sessions/{thread_id}/messages/message_index.json` | `sessions/{thread_id}/messages/part-*.jsonl` |
| `sessions/{thread_id}/runs_index.json` | `sessions/{thread_id}/manifest.json` + `runs/*/manifest.json` |
| `event_index.json` | `events/part-*.jsonl` |
| `leaf_state.json` | `events/part-*.jsonl` + `operations.jsonl` |
| `runs_index.json` | `runs/*/manifest.json` + `leaf_state.json` |
| `jobs/{job_id}/event_index.json` | `jobs/{job_id}/events/part-*.jsonl` |
| `jobs/{job_id}/leaf_state.json` | `jobs/{job_id}/events/part-*.jsonl` + Job manifest |
| `jobs_index.json` | `jobs/*/manifest.json` + `jobs/*/leaf_state.json` |
| `documents_index.json` | `documents/*/manifest.json` + `versions.json` |
| `memory_index.json` | `memory/*.json` |

索引重建必须写审计事件：

```json
{
  "event_type": "index_rebuilt",
  "run_id": "run_001",
  "target": "event_index.json",
  "reason": "index_missing",
  "rebuilt_event_count": 120,
  "warning_count": 0
}
```

## 并发写保护

由于 Redis 不做锁，P0 的并发写保护放在 Runtime 和 MinIO 索引对象中完成：

- 同一个 run 只能有一个 `EventStoreWriter`。
- 所有 Tool、MCP、SubAgent 事件先进入 Runtime event bus，再由 EventStoreWriter 排序落盘。
- `manifest.json` 中保存 `owner.fencing_token`，防止两个 Runtime 同时接管。
- `event_index.json`、`leaf_state.json`、`runs_index.json` 都有 `revision`。
- 更新索引时使用 etag / revision 乐观并发控制。
- SubAgent 写任务必须声明互不重叠 `write_scope`。
- 无法证明 `write_scope` 不重叠时，任务必须串行。
