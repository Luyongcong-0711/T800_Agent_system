本项目不会照搬 Hermes 的 SQLite/session DB/Gateway 实现。本项目对应落地方式：

- Hermes 的 session DB 压缩锁在本项目中落为 `MinIO compaction_lock.json + 条件写入/版本号 + run_id holder`。
- Hermes 的 session rotation 在本项目中落为 `compaction entry + parent_compaction_id + source_message_ids + leaf_state.json`，不另起旧式会话数据库。
- Hermes 的 memory flush 在本项目中落为 `memory_snapshot` 和 `memory candidate extraction` 写入 MinIO JSON / JSONL，再同步 Milvus / Neo4j。
- Hermes 的 summary 失败处理在本项目中落为 `ToolResult/RunEvent` 可见错误、降级裁剪、最多一次 compact-and-retry，不允许静默丢弃中间历史。

| 类型 | 作用 |
| --- | --- |
| System Prompt | 定义 Agent 身份、边界、规则 |
| Short-term Memory | 当前任务上下文、最近消息、临时状态 |
| Long-term Memory | 用户偏好、项目知识、可复用经验 |
| Context | 当前模型调用实际拼接进去的信息 |
| Compaction | 长上下文压缩和摘要 |

## OpenClaw 与 Hermes 的记忆实现观察

OpenClaw 倾向把长期记忆落到工作区文件中，再通过专门工具检索和读取。它的模式可以概括为：

- 使用 Markdown 文件保存可读长期记忆。
- 通过 `memory_search` 搜索记忆摘要或片段。
- 通过 `memory_get` 读取具体内容。
- 记忆内容可以被索引，检索时返回路径、行号、分数或片段。
- 主动写记忆通常需要工具或插件链路，不应让模型随意写入。

Hermes 倾向把用户和全局偏好整理到少量 curated memory 文件，并配合会话搜索。它的模式可以概括为：

- 使用 `USER.md` 保存用户身份、称呼、偏好、长期稳定信息，并限制体积。
- 使用 `MEMORY.md` 保存系统长期记忆、经验和可复用上下文，并限制体积。
- 这两个文件存放在本地 memories 目录中，`MEMORY.md` 约 2200 字符，`USER.md` 约 1375 字符，目的是让“每次都进入提示词”的内容保持很小。
- 会话历史通过 `session_search` 检索，不等同于长期记忆。
- 记忆工具负责新增、替换、删除和查询，避免模型直接编辑原始记忆文件。
- 会话开始时注入的是经过整理的记忆快照，不是把所有历史对话塞进上下文。
- 记忆写入前会检查注入、外泄和隐藏字符等风险，因为这些记忆后续会进入系统提示。
- 上下文压缩由独立的 context engine 决定何时触发和如何压缩，可替换为其他压缩实现。

对本系统的启发：

- 用户名字、爱好、偏好需要有明确的长期记忆对象。
- 搜索和读取要分离，先搜摘要，再按需回源。
- `user_profile` / `user_preference` 自动写入不走审批，但必须有来源证据、前端可见、可修改、可删除。
- 会话历史检索和长期记忆不是一回事。
- 长期记忆应该可查看、可删除、可修正。
- 被启用的长期记忆会进入后续模型调用的 memory snapshot，作为大模型可见的长期记忆上下文。

## 本系统长期记忆存储

当前决策：

- 长期记忆原文以 MinIO JSON 保存，MinIO 是权威存储。
- `user_profile` / `user_preference` 是独立记忆类型，用于保存用户名字、称呼、爱好、偏好。
- `user_profile` 永远是 `global` scope。
- `user_preference` 支持 `global` 和 `workspace` 两种 scope。
- `project_fact` / `project_rule` 永远是 `workspace` scope。
- `user_profile` / `user_preference` 自动写入不需要审批，但必须前端可见。
- 用户可以在前端查看、修改、删除这些长期记忆。
- 被启用的 `user_profile` / `user_preference` 会进入后续模型调用的 memory snapshot。
- 需要语义搜索的记忆同步写入 Milvus。
- 涉及稳定实体关系的记忆同步写入 Neo4j。
- `memory_search` 只返回摘要。
- `memory_get` 才读取详情。
- 写长期记忆需要 Hook。
- 密钥、token、密码、身份证号、银行卡等敏感内容默认不自动保存为长期记忆。

## 用户名字、爱好、偏好的存放方式

| 内容 | MinIO | Milvus | Neo4j |
| --- | --- | --- | --- |
| 用户名字 | global `user_profile` canonical JSON 原文，路径 `users/{user_id}/profile/{memory_id}.json` | 可选，用于语义搜索 | User 节点属性 |

## 记忆工具 LangChain 规格

模型不能直接改 MinIO memory JSON、Milvus memory collection 或 Neo4j 记忆节点。长期记忆相关能力必须通过 LangChain Tool 进入 Runtime，再由 Hook、敏感内容过滤、索引同步和事件日志统一处理。

公共参数：

```python
from langchain_core.tools import tool
from pydantic import BaseModel, Field

class MemoryScopeArgs(BaseModel):
    workspace_id: str
    user_id: str

def finish_memory_tool(tool_name: str, result: ToolResult, params_preview: dict | None = None) -> dict:
    runtime_services.audit_log.write_tool_event(
        tool_name,
        params_preview=redact(params_preview or {}),
        result_summary=summarize_result(result),
    )
    return result.to_dict()
```

`memory_search` 只返回摘要和 ID，不返回完整敏感内容：

```python
class MemorySearchArgs(MemoryScopeArgs):
    query: str
    memory_types: list[str] = Field(default_factory=list)
    limit: int = Field(default=8, ge=1, le=20)

@tool("memory_search", args_schema=MemorySearchArgs)
def memory_search_tool(
    workspace_id: str,
    user_id: str,
    query: str,
    memory_types: list[str] | None = None,
    limit: int = 8,
) -> dict:
    """搜索长期记忆摘要，返回 memory_id、type、summary、score 和敏感标记。"""
    assert_user_scope(user_id, workspace_id)
    hits = memory_service.search(
        workspace_id=workspace_id,
        user_id=user_id,
        query=query,
        memory_types=filter_allowed_memory_types(memory_types or []),
        limit=clamp(limit, 1, 20),
    )
    result = ToolResult.ok({"hits": [hit.summary_dict() for hit in hits]})
    return finish_memory_tool("memory_search", result, {"query": query, "memory_types": memory_types})
```

`memory_get` 按 ID 回源读取详情，但必须做权限和敏感内容过滤：

```python
class MemoryGetArgs(MemoryScopeArgs):
    memory_id: str
    include_source: bool = True

@tool("memory_get", args_schema=MemoryGetArgs)
def memory_get_tool(
    workspace_id: str,
    user_id: str,
    memory_id: str,
    include_source: bool = True,
) -> dict:
    """读取单条长期记忆详情，用于回答前确认具体偏好、资料或项目事实。"""
    assert_user_scope(user_id, workspace_id)
    memory = memory_service.get(memory_id)
    assert_memory_visible_to_user(memory, user_id, workspace_id)
    data = memory.public_dict(include_source=include_source)
    result = ToolResult.ok(data)
    return finish_memory_tool("memory_get", result, {"memory_id": memory_id})
```

`memory_upsert` 是唯一允许模型发起写记忆的工具入口。`user_profile` / `user_preference` 不弹审批，但必须前端可见、可删除、可禁用模型注入；其他类型是否审批由 Hook 决定。

```python
class MemoryUpsertArgs(MemoryScopeArgs):
    memory_type: str = Field(..., description="user_profile / user_preference / project_fact / project_rule 等")
    field: str | None = None
    summary: str
    content: str
    source_thread_id: str
    source_message_id: str
    evidence: str
    confidence: float = Field(default=0.8, ge=0, le=1)
    enabled_for_model_context: bool = True

@tool("memory_upsert", args_schema=MemoryUpsertArgs)
def memory_upsert_tool(**kwargs) -> dict:
    """写入或更新长期记忆；用户资料和偏好自动保存，敏感或高风险内容进入 Hook 策略。"""
    assert_user_scope(kwargs["user_id"], kwargs["workspace_id"])
    candidate = MemoryCandidate.from_tool_args(kwargs)
    hook_result = memory_hook.before_memory_write(candidate)
    if hook_result.blocked:
        return finish_memory_tool("memory_upsert", ToolResult.blocked(hook_result.reason), {"memory_type": candidate.type})

    if candidate.type in {"user_profile", "user_preference"}:
        candidate.requires_approval = False
        candidate.frontend_visible = True

    memory = memory_service.upsert_canonical_json(candidate)
    if memory.should_index_to_milvus:
        memory_indexer.upsert_vector(memory)
    if memory.should_index_to_neo4j:
        memory_graph_writer.upsert_relationship_fact(memory)
    event_store.append_memory_event(memory.to_event("memory_upserted"))
    result = ToolResult.ok(memory.public_dict(include_source=True))
    return finish_memory_tool("memory_upsert", result, {"memory_type": memory.type, "memory_id": memory.memory_id})
```

`memory_delete` 默认是用户可见操作。删除或禁用后，下一次模型调用的 `memory_snapshot` 不能再包含对应 `memory_id`。

```python
class MemoryDeleteArgs(MemoryScopeArgs):
    memory_id: str
    mode: str = Field(default="disable", description="disable 或 delete")
    reason: str | None = None

@tool("memory_delete", args_schema=MemoryDeleteArgs)
def memory_delete_tool(
    workspace_id: str,
    user_id: str,
    memory_id: str,
    mode: str = "disable",
    reason: str | None = None,
) -> dict:
    """禁用或删除长期记忆，并同步更新索引和后续 memory snapshot。"""
    assert_user_scope(user_id, workspace_id)
    memory = memory_service.get(memory_id)
    assert_memory_visible_to_user(memory, user_id, workspace_id)
    result_memory = memory_service.disable_or_delete(memory, mode=mode, reason=reason)
    memory_indexer.delete(memory_id)
    memory_graph_writer.disable(memory_id)
    event_store.append_memory_event(result_memory.to_event("memory_disabled_or_deleted"))
    result = ToolResult.ok({"memory_id": memory_id, "mode": mode, "enabled_for_model_context": False})
    return finish_memory_tool("memory_delete", result, {"memory_id": memory_id, "mode": mode})
```

## 写记忆 Hook

自动写记忆前必须判断：

- 是否是长期稳定事实。
- 是否来自用户明确表达。
- 是否可能是临时偏好。
- 是否涉及隐私或敏感内容。
- 是否已存在相同或冲突记忆。

P0 采用“模型判断 + 受控工具写入”的策略。系统不使用硬编码规则枚举所有可记忆内容，而是在 Runtime system prompt 和 Tool 描述中要求模型主动判断：哪些用户信息、偏好、项目事实或项目规则未来会复用，就调用 `memory_upsert` 写入长期记忆。

模型可主动写入的典型内容：

| 类型 | 示例 | 默认审批 |
| --- | --- | --- |
| `user_profile` | 用户名字、称呼、身份中用户明确愿意保存的部分 | 不审批，前端可见 |
| `user_preference` | 回复语言、回答风格、工具偏好、常用流程偏好 | 不审批，前端可见 |
| `project_fact` | 当前项目技术栈、目录约定、数据库选型 | Hook 判断，通常可直接写 |
| `project_rule` | 用户明确要求后续必须遵守的项目规则 | Hook 判断，必要时确认 |
| `correction` | 用户纠正“不是 Java，是 LangChain + LangGraph” | Hook 判断，通常可直接写 |

模型不应该写入的内容：

- 明显临时的一次性要求。
- 模糊猜测出来的隐私。
- API key、token、密码、私钥和数据库凭据。
- 用户要求不要保存的内容。
- 与用户已删除或禁用的记忆等价的内容，除非用户重新明确要求保存。

模型判断流程：

```text
每轮对话结束前或压缩前
  -> Runtime 提供最近用户消息、当前任务摘要、已有相关记忆摘要
  -> 模型判断是否存在可复用稳定信息
  -> 如果没有，什么都不做
  -> 如果有，调用 memory_upsert
  -> Hook 做敏感扫描、去重、冲突检测、删除/禁用记忆 deny-list 检查
  -> user_profile / user_preference 直接写入并前端可见
  -> 其他类型按策略直接写入或进入待确认
```

为了避免用户删除后又被模型写回来，P0 增加轻量 deny-list：

```text
users/{user_id}/memory/disabled_patterns.json
workspaces/{workspace_id}/memory/disabled_patterns.json
```

用户删除或禁用某条记忆时，系统保存该记忆的 `field`、`summary_hash`、`semantic_hash` 和原因。后续 `memory_upsert` 命中 deny-list 时，默认阻止写入并返回 `memory_previously_disabled`，除非用户在当前对话里明确表示“重新记住这个”。

写入流程：

```text
候选记忆生成
  -> 去重和冲突检测
  -> 敏感性判断
  -> user_profile / user_preference 直接写入并前端可见
  -> 其他类型按策略进入待确认或直接写入
  -> MinIO 保存 canonical JSON
  -> 可选写入 Milvus
  -> 可选写入 Neo4j
  -> 写 memory event
```

`user_profile` / `user_preference` 写入规则：

- 不需要审批弹窗。
- 必须写入来源证据。
- 必须在 Memory 页面可见。
- 用户可以删除、修正、禁用模型上下文注入。
- 删除或禁用后，后续模型调用不再注入该记忆。
- 修正后需要更新 MinIO 权威 JSON，并刷新 Milvus / Neo4j 对应索引。

不自动保存为长期记忆的内容：

- API key、token、密码、私钥。
- 身份证号、银行卡号等强敏感标识。
- 用户未明确表达的推断性隐私。
- 明显临时的偏好，例如“这次先简单点”。

## 模型记忆注入

长期记忆不是只存起来，还要能在后续模型调用时成为模型可见上下文。

每次模型调用前，Runtime 构建 `memory_snapshot`：

```text
global user_profile active entries
global user_preference active entries
当前 workspace 的 user_preference active entries
当前 workspace 的 project_rule / project_fact 摘要
按当前问题检索到的 memory_search 结果摘要
```

注入原则：

- `user_profile` / `user_preference` 中 `enabled_for_model_context=true` 的记录默认注入。
- global scope 记忆可跨 thread、跨 workspace 注入；workspace scope 记忆只在当前 `workspace_id` 下进入模型上下文。
- 注入内容使用摘要和结构化字段，不直接塞入完整历史对话。
- 用户在前端删除或禁用后，下一次模型调用必须停止注入。
- memory snapshot 需要记录来源 memory_id，便于回答后追踪模型看到了哪些记忆。
- memory snapshot 可以随模型请求一起发送给大模型，因此写入前必须做敏感内容过滤。
- 新建 thread 时不注入旧 thread 的短期消息历史。
- 旧 thread 的 compaction 不自动进入新 thread。
- 跨 thread 默认注入的只有启用状态的长期记忆，例如 `user_profile`、`user_preference` 和相关项目长期记忆摘要。

示例：

```json
{
  "memory_snapshot_id": "memsnap_001",
  "user_id": "user_001",
  "thread_id": "thread_010",
  "included_memory_ids": ["mem_profile_name_001", "mem_pref_style_001"],
  "profile": {
    "name": "张三"
  },
  "preferences": [
    "用户偏好中文、直接、少占位的回答风格。"
  ],
  "created_at": "2026-05-29T00:00:00Z"
}
```

## 多对话窗口与会话历史

多对话窗口下必须区分三类内容：

| 类型 | 范围 | 是否自动进入新对话 |
| --- | --- | --- |
| 当前 thread 短期消息 | 单个 thread | 否 |
| 当前 thread compaction | 单个 thread | 否 |
| Long-term Memory | 用户 / 工作区 / 项目 | 是，受 `enabled_for_model_context` 控制 |

规则：

- `thread_id` 代表一个可见对话窗口。
- 新 thread 默认没有旧 thread 的 short-term memory。
- 当前 thread 的历史消息和 compaction 只用于当前 thread 后续模型调用。
- 旧 thread 历史不会因为创建新 thread 被删除。
- 旧 thread 历史不自动变成长期记忆。
- 如果用户明确要求“查一下之前哪个对话说过”，才使用会话历史检索工具。
- 会话历史检索返回 thread_id、message_id、摘要和来源，不直接把整段历史塞进上下文。

### session_search LangChain Tool

`session_search` 用于搜索历史 thread 摘要或消息片段。它不是长期记忆工具，不能替代 `memory_search`。

```python
class SessionSearchArgs(BaseModel):
    workspace_id: str
    user_id: str
    query: str
    thread_status: list[str] = Field(default_factory=lambda: ["active", "archived"])
    limit: int = Field(default=10, ge=1, le=20)

@tool("session_search", args_schema=SessionSearchArgs)
def session_search_tool(
    workspace_id: str,
    user_id: str,
    query: str,
    thread_status: list[str] | None = None,
    limit: int = 10,
) -> dict:
    """搜索用户历史对话摘要和消息片段，返回可回源的 thread_id / message_id。"""
    assert_user_can_read_workspace(user_id, workspace_id)
    hits = session_history_service.search(
        workspace_id=workspace_id,
        user_id=user_id,
        query=query,
        statuses=thread_status or ["active", "archived"],
        limit=clamp(limit, 1, 20),
    )
    result = ToolResult.ok({
        "hits": [hit.public_summary() for hit in hits],
        "warning": "session_search 结果不会自动写入长期记忆"
    })
    return finish_memory_tool("session_search", result, {"query": query})
```

### session_message_get LangChain Tool

`session_message_get` 用于按 message_id 回源读取旧对话片段。

```python
class SessionMessageGetArgs(BaseModel):

    user_id: str

```

## 上下文压缩

上下文压缩解决的是当前对话太长的问题，不等同于长期记忆。

当前决策：上下文压缩采用 Hermes 默认在线压缩策略。第一版实现 `ContextCompressor` 风格的工程版本，不把完整 LCM / Summary DAG 作为 P0。

核心形态：

```text
原始 messages
  -> 压缩旧工具结果
  -> 保留 head 原文
  -> 保留 tail 原文
  -> 中间历史生成结构化 summary
  -> 下一轮上下文 = head + summary + tail
```

## ContextEngine 接口

压缩算法不直接散落在 Agent Runtime 中，而是通过 `ContextEngine` 接口挂载。P0 默认 engine 固定为 Hermes 风格 `ContextCompressor`。

```python
class ContextEngine:
    def update_from_response(self, usage: dict) -> None:
        ...

    def should_compress(self, prompt_tokens: int, model_context_limit: int) -> bool:
        ...

    def compress(self, messages: list[dict], current_tokens: int, focus_topic: str | None = None) -> tuple[list[dict], dict]:
        ...
```

LangGraph 接入方式：

```python
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class ContextState(TypedDict):
    workspace_id: str
    user_id: str
    thread_id: str
    run_id: str
    messages: list[dict]
    memory_snapshot: dict
    prompt_tokens: int
    context_window_tokens: int
    max_output_tokens: int
    compaction: dict | None
    warnings: list[str]

def build_memory_snapshot_node(state: ContextState) -> dict:
    snapshot = memory_snapshot_builder.build(
        workspace_id=state["workspace_id"],
        user_id=state["user_id"],
        thread_id=state["thread_id"],
        query=latest_user_message(state["messages"]),
    )
    minio.write_json(memory_snapshot_key(state["thread_id"], snapshot["memory_snapshot_id"]), snapshot)
    return {"memory_snapshot": snapshot}

def count_tokens_node(state: ContextState) -> dict:
    prompt_tokens = token_counter.count_messages(
        messages=state["messages"],
        memory_snapshot=state["memory_snapshot"],
    )
    return {"prompt_tokens": prompt_tokens}

def route_after_token_count(state: ContextState) -> str:
    usable_budget = state["context_window_tokens"] - state["max_output_tokens"]
    if state["prompt_tokens"] + state["max_output_tokens"] > state["context_window_tokens"]:
        return "compress"
    if context_engine.should_compress(state["prompt_tokens"], usable_budget):
        return "compress"
    return "skip"

def hermes_compaction_node(state: ContextState) -> dict:
    compacted_messages, compaction_object = context_engine.compress(
        messages=state["messages"],
        current_tokens=state["prompt_tokens"],
        focus_topic=latest_user_message(state["messages"]),
    )
    minio.write_json(compaction_key(state["thread_id"], compaction_object["compaction_id"]), compaction_object)
    event_store.append_event(state["run_id"], {
        "type": "compaction_created",
        "compaction_id": compaction_object["compaction_id"],
        "strategy": compaction_object["strategy"],
    })
    return {"messages": compacted_messages, "compaction": compaction_object}

context_builder = StateGraph(ContextState)
context_builder.add_node("build_memory_snapshot", build_memory_snapshot_node)
context_builder.add_node("count_tokens", count_tokens_node)
context_builder.add_node("hermes_compaction", hermes_compaction_node)
context_builder.add_edge(START, "build_memory_snapshot")
context_builder.add_edge("build_memory_snapshot", "count_tokens")
context_builder.add_conditional_edges(
    "count_tokens",
    route_after_token_count,
    {"compress": "hermes_compaction", "skip": END},
)
context_builder.add_edge("hermes_compaction", END)
context_preflight_graph = context_builder.compile(checkpointer=runtime_checkpointer)

def run_context_preflight(context_state: ContextState) -> ContextState:
    return context_preflight_graph.invoke(
        context_state,
        config={"configurable": {"thread_id": context_state["thread_id"]}},
    )
```

第一版内置：

| Engine | 用途 |
| --- | --- |
| HermesStyleContextCompressor | P0 默认在线压缩 |
| ToolResultCompressor | 先压缩旧工具结果 |
| NoCompressionEngine | 调试和小上下文场景 |

后续可扩展：

| Engine | 用途 |
| --- | --- |
| LCMStyleEngine | 原文落库、摘要 DAG、搜索展开 |
| CustomProviderEngine | 接入自定义压缩 provider |

## Hermes 默认压缩参数

P0 直接采用 Hermes 默认在线压缩机制。

压缩配置：

```json
{
  "compression": {
    "enabled": true,
    "threshold": 0.50,
    "target_ratio": 0.20,
    "protect_last_n": 20
  },
  "auxiliary": {
    "compression": {
      "provider": "auto",
      "model": null,
      "base_url": null
    }
  }
}
```

参数含义：

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `threshold` | `0.50` | prompt tokens 达到模型上下文窗口 50% 时触发压缩 |
| `target_ratio` | `0.20` | tail token 保护预算 = threshold_tokens * 0.20 |
| `protect_last_n` | `20` | 至少保护最近 20 条消息 |
| `protect_first_n` | `3` | 保护开头 3 条消息，包含 system 和最初交互 |

计算示例：

```text
context_window_tokens = 200000
max_output_tokens = 8192
usable_input_budget = 191808
threshold_tokens = 200000 * 0.50 = 100000
tail_token_budget = 100000 * 0.20 = 20000
max_summary_tokens = min(200000 * 0.05, 12000) = 10000
```

`context_window_tokens` 和 `max_output_tokens` 来自模型 API 配置。系统默认分别为 `200000` 和 `8192`，用户可以在 API 配置页面修改。

触发策略：

- Agent ContextCompressor 使用准确 token 计数，在达到 `compression.threshold` 时触发，默认 50%。
- 不做中间 context pressure warning，避免模型因为“上下文压力提示”过早放弃复杂任务。
- session hygiene 作为二级保护，在模型上下文窗口 85% 时触发，用于捕捉跨轮积累导致的超大 session。
- 工具结果过长时，先做工具结果裁剪，再决定是否进行对话摘要压缩。
- 如果 `prompt_tokens + max_output_tokens > context_window_tokens`，必须先压缩、裁剪可回源证据或拒绝本次调用。

## Hermes 风格压缩结构

压缩后的 messages 结构：

```text
system / developer 原文
最早几条关键原文
[CONTEXT COMPACTION - REFERENCE ONLY]
  ## Active Task
  ## User Goal
  ## Constraints
  ## Current State
  ## Completed Actions
  ## Failed Attempts
  ## Tool Results
  ## Files / Resources Mentioned
  ## Decisions
  ## Open Questions
  ## Remaining Work
最近 N 轮原文
```

head 原文保留：

- system / developer 指令。
- 用户最初目标。
- 长期偏好。
- 项目硬约束。
- 当前任务边界。

tail 原文保留：

- 用户最近修正。
- 最近失败的工具调用。
- 当前正在编辑的文件。
- 刚刚产生的错误。
- 当前未完成的审批或工具调用。

middle 压缩为结构化 summary：

- 做过什么。
- 为什么这么做。
- 得到了什么结论。
- 哪些路径已经排除。
- 还有什么没做。
- 哪些文件、对象、trace、tool result 可以回源。

## 工具结果压缩

在调用摘要模型前，先对旧工具结果做低成本压缩。

示例：

```text
原始：shell 输出 3000 行
压缩：[terminal] ran `pytest tests/` -> exit 1, 3000 lines output

原始：read_file 返回完整大文件
压缩：[read_file] read app.py from line 1, 12340 chars

原始：search_files 返回大量命中
压缩：[search_files] query="ContextCompressor" -> 12 matches
```

原则：

- 原始工具结果写入日志或对象存储。
- 模型上下文只保留工具做过什么、路径、命令、退出码、数量级和摘要。
- protected tail 之外的旧工具结果如果超过长度阈值，替换为短占位摘要。
- tool_call / tool_result 成对关系不能被拆坏；边界需要向前或向后对齐，避免留下孤儿 tool result。
- 需要细节时通过日志工具、对象工具或上下文展开工具回源。
- 不让单次工具输出挤爆上下文。

## 压缩模型配置

第一版预留独立压缩模型配置，即使初期复用主模型，也不写死。

```json
{
  "compression": {
    "provider": "same_as_main",
    "model": "same_as_main",
    "max_input_tokens": 120000,
    "max_output_tokens": 8192,
    "temperature": 0,
    "enabled": true
  }
}
```

压缩模型要求：

- 上下文窗口足够大。
- 压缩模型上下文窗口最好不小于主模型上下文窗口。
- 输出格式稳定。
- 成本低于主推理模型更好。
- 压缩模型上下文不足时，不能静默丢失关键中间历史；必须记录错误并降级为更保守的工具结果裁剪和用户可见告警。

摘要预算：

```text
summary_tokens = content_tokens * 0.20
min_summary_tokens = 2000
max_summary_tokens = min(context_length * 0.05, 12000)
```

重复压缩：

- 第一次压缩生成结构化 summary。
- 后续压缩不从零总结，而是把 previous_summary 交给压缩模型更新。
- 新进展加入 summary，已完成事项移动到 Done，过期信息删除。

压缩保留：

- 系统规则。
- 用户最新目标。
- 已确认决策。
- 未解决问题。
- 当前计划和步骤状态。
- 关键工具结果摘要。
- open approvals。
- pending tool calls。
- 最近 N 轮原始对话。

压缩丢弃或转摘要：

- 旧 token 流。
- 冗长工具 stdout。
- 重复检索结果。
- 已完成且无后续依赖的中间推理。
- 可从 MinIO 回源的大段文档内容。

```text
workspaces/{workspace_id}/sessions/{thread_id}/compactions/{compaction_id}.json
```

压缩摘要不能成为唯一历史。原始消息、原始工具结果和摘要之间必须通过 ID 关联。

## Compaction 与长期记忆的区别

| 项目 | Compaction | Long-term Memory |
| --- | --- | --- |
| 目标 | 压缩当前会话上下文 | 跨会话复用稳定信息 |
| 生命周期 | 会话级或任务级 | 长期 |
| 是否默认检索 | 当前会话优先使用 | 按需搜索 |
| 是否用户可管理 | 可查看摘要 | 必须可查看、可删除、可修正 |
| 是否写入 Milvus | 默认不一定 | 需要语义搜索时写入 |
| 是否写入 Neo4j | 默认不一定 | 涉及实体关系时写入 |

压缩摘要默认不自动提升为长期记忆。只有摘要中出现稳定事实、用户资料、用户偏好、项目规则等内容时，Runtime 才抽取候选记忆，再按长期记忆流程写入 `user_profile`、`user_preference` 或项目记忆。

## LCM 风格后续路线

完整 LCM 不放在 P0。后续如果需要“旧上下文可搜索、可展开、可追溯”，再增加：

- raw message store。
- 全文索引。
- summary node。
- source lineage。
- `memory_grep` / `memory_expand` / `memory_status` 工具。
- 分页展开，避免一次把旧上下文全部塞回模型。

当前第一版只实现 Hermes 默认在线压缩策略。
